### 1. [high] site/src/lib/email/send.ts:134
**Problem:** Account emails are sent through Brevo, whose link rewriting cannot be switched off on the free or standard plan (design/accounts/research-brevo-sending.md:133,220-222). Every `/account/password/?t=<token_hash>&k=<kind>` link is therefore rewritten through Brevo's redirector and the destination URL is stored in Brevo's transactional event log, where `GET /v3/smtp/statistics/events` returns it in the `link` field. That token is a full account-takeover credential for an hour: verifyOtp -> updateUser({password}) needs nothing else. The research flagged the rewrite only as a cosmetic problem and a token-burn risk; nobody named the fact that the token is retained by a third party. The same BREVO_API_KEY is the low-stakes marketing-list key, so a key whose blast radius was 'can write to a mailing list' is now 'can take over any account that signed up recently'. 'Anonymous email tracking' does not help: the research confirms it unlinks the click from the contact but does not stop the rewrite or the storage of the URL.
**Scenario:** The BREVO_API_KEY leaks (pasted into a support ticket, read from a Vercel env dump, or Brevo itself is breached). The holder calls GET https://api.brevo.com/v3/smtp/statistics/events?event=clicks and reads live `/account/password/?t=...&k=signup` links for everyone who signed up in the last hour. They open one, set a password of their choosing, sign in as that person and read their stored result codes, which decode to that person's position on six theology axes. The victim sees nothing: `signOut({scope:'local'})` is the only sign-out the site performs, so no session is revoked, and their own password still works.
**Fix:** Send account email through Resend rather than Brevo. send.ts already prefers RESEND_API_KEY over BREVO_API_KEY, so this is an env change plus a Resend domain with click tracking off (Resend's default). Keep Brevo for the marketing list only, on a separate key. If Brevo must carry account mail: cut the OTP lifetime from 3600s to about 600s in Supabase (Authentication -> Sessions, mailer_otp_exp) so the window in Brevo's log is short, issue a Brevo key used for nothing else, and say in site/src/lib/account/README.md that the Brevo key is an account-takeover-grade secret.

### 2. [high] site/src/lib/account/schema.sql:171
**Problem:** The 2,000-row ceiling on public.results does not bound anything. Two gaps: (1) `grant select, insert on public.results to authenticated` (line 160) grants insert on EVERY column including `deleted_at`, and the trigger counts only `where deleted_at is null`, so rows inserted already-tombstoned never trip the cap; `grant update (deleted_at)` (line 161) then lets the same user PATCH them back to null, and the trigger is BEFORE INSERT only, so the update is unchecked. (2) Even without that, the cap counts live rows while nothing ever purges tombstones, so insert-2000 / mark-all-deleted / repeat grows the table without limit. `taken_at` is client-supplied and part of the primary key, so there is no natural collision to stop it.
**Scenario:** Anyone makes a free account, reads PUBLIC_SUPABASE_KEY out of the page bundle and the bearer out of ww.auth, then POSTs batches to /rest/v1/results with `deleted_at` set to now(). RLS passes every row (user_id = auth.uid()), the trigger never fires, and a few hundred thousand rows fill the free plan's 500 MB. Supabase puts the database into read-only enforcement: nobody can sign up, nobody's results sync, and /me/ stops agreeing with the account for every real user at once. The attacker then PATCHes deleted_at=null and their own account holds unlimited live rows too.
**Fix:** Enforce the ceiling on total rows, not live ones, and on UPDATE as well as INSERT: make the trigger `before insert or update on public.results`, count `where user_id = new.user_id` with no deleted_at filter, and drop `deleted_at` from the insert grant with `grant insert (user_id, quiz, code, taken_at) on public.results to authenticated`. Add a second guard the trigger cannot be raced past — a `check (deleted_at is null or deleted_at >= created_at)` is not enough; the real one is a periodic purge of tombstones older than the sync window (TOMBSTONE_LIMIT only ever reads the most recent 200 anyway), which the daily /api/auth/health?ping=1 job is already positioned to run.

### 3. [high] site/src/lib/account/client.ts:194
**Problem:** `requestLink` and `requestReset` call Supabase's /auth/v1/otp and /auth/v1/recover directly from the browser with the publishable key, with no CAPTCHA. The honeypot fields on sign-up.astro, sign-in.astro and forgot.astro are client-side decoration: the request never passes through this site's server, so an attacker skips the page entirely and posts to the Supabase endpoint with the key lifted from the page bundle. The research scoped Supabase's CAPTCHA and deliberately deferred it (research-supabase-auth-flow.md:204), and README step 9 then tells the owner to raise the email ceiling to 100 per hour, which widens the hole rather than narrowing it.
**Scenario:** A script loops over addresses at 100/hour against Brevo's free 300/day cap. Within about three hours every day the quota is gone, and from then on real sign-ups, password resets and 'send it again' all fail silently: the hook answers 200 with a log row, the reader sees 'Check your email' and no email ever arrives. Separately, one chosen third-party address can be mailed once a minute from account@wiserwalk.com; a handful of spam complaints from that gets the Brevo sender suspended, which kills sign-in for everyone including existing accounts.
**Fix:** Turn on Supabase's bot protection (Settings -> Authentication -> Bot and Abuse Protection, Cloudflare Turnstile) and pass the token through: `signInWithOtp({ email, options: { captchaToken } })`, `resetPasswordForEmail(email, { captchaToken })` and `signInWithPassword({ email, password, options: { captchaToken } })` in client.ts. It is the only control that sits in front of the endpoint the attacker actually calls. Until that ships, set the emails-per-hour limit to the lowest number that serves real traffic rather than 100, so an abuse day costs a fraction of the Brevo quota instead of all of it.

### 4. [medium] site/src/pages/me.astro:458
**Problem:** The sign-up box on /me/ redirects to `/account/check-email/?to=${encodeURIComponent(email)}`, putting the reader's email address in the URL. check-email.astro reads the address only from sessionStorage (`site/src/pages/account/check-email.astro:98`) and never looks at `?to=`, so the parameter is pure leakage with no consumer. It also contradicts that page's own documented rule ('The address comes out of sessionStorage... NOT out of the URL... it would also have been in a server log, and there is no reason for it to be', check-email.astro:10-13), the brief's no-address-in-URLs rule, and the sibling pages sign-up.astro:179, forgot.astro:102 and password.astro:277, which all do it correctly. /me/ is where the header's 'My results' mark points, so this is the main sign-up path, not an edge case.
**Scenario:** Somebody signs up from /me/. Their address is written into their browser history (shared laptop, synced history), into Vercel's request log for that deployment, and into any corporate or school TLS-inspecting proxy's access log. On the page itself they are shown 'the address you gave us' instead of what they typed, which is the exact typo-catching the page was built for, and pressing 'Send it again' answers 'We do not know which address to send to. Go back and put it in again.' — so the leak buys nothing and breaks the page.
**Fix:** In me.astro replace the redirect with `try { sessionStorage.setItem('ww.acct.to', email); } catch (e) {}` followed by `window.location.href = '/account/check-email/';`, matching sign-up.astro:179. Separately, the no-script fallback form on the same panel is `method="get" action="/account/sign-up/"`, which also lands the address in a URL (read back at sign-up.astro:141); that one at least has a consumer, but it should be noted in site/src/lib/account/README.md as the one place an address can reach a server log.

### 5. [medium] site/src/pages/api/auth/health.ts:59
**Problem:** /api/auth/health is a public, unauthenticated, unrate-limited route (prerender = false, no origin check, no secret) that returns the owner's whole configuration state as JSON and fans one inbound request out to four outbound ones. A plain GET reports whether each of the four keys is set, whether SUPABASE_SECRET_KEY was mistakenly given the publishable value, whether the hook secret looks well-formed, whether the project is paused or refusing keys, whether the schema has been run, whether the site was rebuilt after the keys were pasted, whether the sending domain has a verified sender, and how long ago the last account email was asked for and whether it went out. `?ping=1` additionally runs a DELETE against auth_email_log with no auth. The comment argues the ping needs no secret, which is fair for the ping alone, but the same handler serves the full report.
**Scenario:** An attacker polls the JSON during the setup window and sees the exact moment PUBLIC_SUPABASE_URL and SUPABASE_SECRET_KEY are live while SUPABASE_EMAIL_HOOK_SECRET is still 'todo' — the window in which /api/auth/email answers 503 and the schema is reachable but the hook is unprotected in the owner's mind rather than in code. Independently, a loop at a few requests a second costs one Brevo /v3/senders call and three Supabase calls each, which throttles the Brevo API key the account emails share and burns Vercel invocations, while `?ping=1` gives an unauthenticated DELETE loop.
**Fix:** Gate both modes behind Vercel's own cron secret: set CRON_SECRET in Vercel (Vercel then sends `Authorization: Bearer <CRON_SECRET>` on cron requests) and return 404 unless the header matches. Give /account/setup/ the same secret through a query parameter the owner pastes once, or accept a signed-in admin check. At minimum, drop everything from the JSON except state and step, and never print the `ago(...)` of the last email or the log's `detail` to an unauthenticated caller.

### 6. [low] site/src/lib/account/checks.ts:234
**Problem:** `checkProject` falls back to the secret key when the publishable key is absent: `const key = trim(env.PUBLIC_SUPABASE_KEY) || trim(env.SUPABASE_SECRET_KEY);`, and then sends it on the `apikey` header to `${projectUrl(env)}/auth/v1/health`. The destination host is whatever PUBLIC_SUPABASE_URL happens to contain, and this check runs on every request to the unauthenticated /api/auth/health. /auth/v1/health needs no key at all, so the fallback buys nothing.
**Scenario:** During setup the owner pastes SUPABASE_SECRET_KEY before the two website values, or mistypes the project ref in PUBLIC_SUPABASE_URL (the README has him copying three values off one screen). Any stranger who then GETs /api/auth/health makes the site hand the service-role secret key, which has BYPASSRLS over every account and every stored result code, to that host on an outbound HTTPS request the owner never sees.
**Fix:** Drop the fallback: call `${base}/auth/v1/health` with no key, or with the publishable key only, and let the 'The two website keys' check be the single thing that reports a missing publishable key. Keep the secret key confined to checkTables and checkHookFired, which genuinely need it.

### 7. [low] site/src/lib/account/emails.ts:63
**Problem:** `originFor` trusts any host ending `.vercel.app` when building the link that carries a live one-time token. I could not turn this into a working attack and want to say so plainly: the request must already carry a valid Standard Webhooks signature to get this far, Vercel routes by Host so a request for a foreign hostname never reaches this function, and Vercel overwrites x-forwarded-host (which Astro's node adapter does otherwise honour, node_modules/astro/dist/core/app/node.js:56-58) with the real one. But the rule is the last line of defence on an account-takeover credential, its safety rests entirely on platform behaviour that is asserted nowhere in the code or in scripts/auth-test.mjs:279, and 'ends in .vercel.app' is a far wider statement than the thing it is meant to permit.
**Scenario:** Any future change that weakens the assumptions — a proxy or edge middleware in front of the function that forwards a client-supplied Host, a wildcard domain added to the Vercel project, or a copy of this handler deployed somewhere with looser routing — turns a signed hook call into an email whose button sends the reader's one-time token to a host of the caller's choosing. Nothing in the test suite would catch it, because the test asserts that a .vercel.app host IS trusted.
**Fix:** Narrow it to what the owner actually needs: exact `wiserwalk.com` and `www.wiserwalk.com`, plus `localhost`/`127.0.0.1`, plus one pinned preview form rather than the whole namespace — either a regex tied to the project (`/^wiser-walk[a-z0-9-]*\.vercel\.app$/`) or, tighter still, an `ACCOUNT_PREVIEW_ORIGIN` env value set only on the Preview environment and compared exactly. Add a test that `https://evil.vercel.app` falls back to HOME_ORIGIN.

## sound
- hook.ts verifyWebhook: I tried to forge one and could not. The HMAC is over the RAW body as `<id>.<timestamp>.<body>`; `sameBytes` rejects unequal lengths and zero-length buffers before timingSafeEqual rather than throwing; an unset, empty, or non-base64 secret decodes to null and is refused, so an empty secret can never verify; `Number(timestamp)` rejects NaN and Infinity and the window is ±300s; a multi-signature header passes only on a `v1,` entry and is refused outright when no v1 entry exists; header lookup is case-insensitive via Headers.get and accepts both webhook-* and svix-* spellings. Replay with a fresh id is impossible because the id is inside the signed string, and replay of the identical request is caught by alreadySent() on the webhook_id primary key (its fail-open is the right trade: a duplicate email beats a person who cannot sign in).
- No header or HTML injection through the hook payload. readPayload bounds and shape-checks every field, `token` must match /^\d{4,8}$/, `action` must be one of three literals or renderAuthEmail returns null, `tokenHash` is encodeURIComponent'd and then esc()'d into a double-quoted attribute, and the recipient address only ever reaches a JSON body field (`to: [msg.to]` / `to: [{email: msg.to}]`), never an SMTP header line.
- Identity in /api/auth/list and /api/auth/delete always comes from whoIs() -> GET /auth/v1/user with the bearer, never from the body; the body carries a boolean and a honeypot string and nothing else. Both routes run sameOrigin() before anything else, and sameOrigin treats a missing Origin header as failure. CSRF is not reachable: a cross-site request can set neither the Authorization header nor a matching Origin.
- Token verification fails closed. checks.ts ask() returns null on abort or throw, whoIs returns null on any non-200, and both routes turn null into 401. A Supabase timeout denies the request rather than letting it through.
- SUPABASE_SECRET_KEY is only ever sent on the `apikey` header (email.ts restHeaders, list.ts stamp, delete.ts, health.ts ping, checks.ts checkTables/checkHookFired), never as a Bearer, never in a URL or a body, never returned to a caller, and never logged. The one exception is the checkProject fallback, reported separately.
- No dynamic innerHTML, set:html, outerHTML, insertAdjacentHTML or document.write anywhere in the new code. The only set:html in Base.astro is JSON.stringify of build-time JSON-LD. Every account page builds DOM with createElement and textContent, including setup.astro's ladder, which prints server-supplied `say` strings as text nodes.
- The one-time token does not survive in the address bar, the history or a Referer. password.astro's inline script runs history.replaceState(null, '', here.pathname), which drops both query and fragment; `<meta name="referrer" content="no-referrer">` is emitted as the first thing in <head> (Base.astro), so even the stylesheet and font requests issued during head parse carry no Referer; the page is noindex, excluded from the sitemap filter in astro.config.mjs, and the analytics beforeSend hook blanks `search` and `hash` for every path starting /account/.
- No open redirect. Nothing in the account flow reads a next, back, redirect or return parameter; every navigation target is a string literal, and neither emailRedirectTo nor redirectTo is ever passed to Supabase, so Supabase's redirect allow list is not load-bearing.
- Account enumeration: sign-up uses signInWithOtp with the default shouldCreateUser: true and forgot uses resetPasswordForEmail, so a known and an unknown address get the same answer and the same page. Sign-in prints one sentence covering both fields. The `unconfirmed` branch in SAYINGS looked like an oracle but is not: GoTrue only returns email_not_confirmed after the password has already matched, and a user created by OTP has no password to match.
- schema.sql row-level security. Every table has RLS enabled, every policy is `to authenticated` and matches `(select auth.uid())`, and each table is revoked from `anon, authenticated` BEFORE any grant — which is the thing that matters on Supabase, where default privileges in the public schema grant ALL on new tables to anon. `anon` ends with nothing on all four tables. auth_email_log has RLS on and no policies at all, so only the secret key (service_role, BYPASSRLS) reaches it. I could not construct a read or write of another user's rows with a valid account and the publishable key.
- Column grants really do hold. A user cannot write profiles.password_set_at or profiles.list_synced_at (only `grant update (notes_off)`), and cannot edit a finished result into a different one: results has no delete grant and no update grant on quiz, code or taken_at, so `grant update (deleted_at)` is the only post-hoc write. The un-delete that grant allows is self-affecting and matters only as the row-cap bypass reported above.
- mark_password_set() is a safe security definer: `set search_path = ''`, every name schema-qualified, no parameters, the row id comes from auth.uid() so it can only ever write the caller's own row, and it is revoked from public and anon before being granted to authenticated. A user calling it early only changes the word on their own /account/ page; nothing on the server trusts password_set_at.
- There is no trigger on auth.users, so nothing on this side can break sign-up inside Supabase where it could not be seen. The only trigger is results_row_cap on public.results, which at worst refuses one save; it is also a security definer with an empty search_path and fully qualified names.
- Nothing key-shaped is committed. I grepped the whole diff for sb_secret, sb_publishable, whsec_, xkeysib-, re_ and JWT-shaped strings; the only hit is the README explaining that the secret key starts `sb_secret_`. console.log/warn appears three times (client.ts:126, send.ts:96, provider.ts consoleProvider) and none of them prints an env value, a token, a key or an address — the preview sender deliberately logs only the kind and the subject.
- auth_email_log is genuinely address-free by construction, not by convention: email.ts record() writes only webhook_id, at, action, ok and a 200-char detail, and send.ts errorWord() extracts a single /^[a-z0-9_.-]{1,48}$/i token from the provider's error body precisely so a provider 400 that quotes the refused address cannot land in the table.
- Account deletion really deletes: DELETE /auth/v1/admin/users/<id> with no body is a hard delete, and profiles, results and game_stats all reference auth.users with `on delete cascade`, so the rows go with the user. The route refuses to report success when SUPABASE_SECRET_KEY is missing, and the MailerLite provider honestly returns 'cannot remove contacts' rather than pretending the list was cleaned.
