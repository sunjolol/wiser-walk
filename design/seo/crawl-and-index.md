# crawl-and-index

The technical floor is genuinely clean: all 97 sitemap URLs return 200 with zero redirects, every canonical is absolute, self-referential and trailing-slash-exact against the sitemap, there are no duplicate titles or descriptions, exactly one H1 per page, lang="en" everywhere, zero orphans, zero broken internal links, and not one internal link points at a redirect, an uppercase path, a query string, www or http. ?theme=dark, ?utm_*, /index.html and /about all canonicalise to the clean URL. Content is fully server-rendered, so nothing depends on JavaScript. http and www each resolve to the apex in one 308 hop, HSTS is on, brotli is on and TTFB is about 100ms. The weakest link is not plumbing, it is what the plumbing is carrying. The 18 tradition pages, which are the Compass's whole search surface, are 48.2% identical to each other measured on five-word shingles (Orthodox vs Catholic reaches 68.5%), run only 327 to 349 words each, and of that roughly 200 words are the same explanatory boilerplate on every one; their titles and descriptions are templates with one name swapped, which is precisely what Google's snippet documentation warns against. The sitemap carries no lastmod at all, which throws away the main crawl-scheduling signal a three-week-old site has. There is no 404 page: a mistyped or stale URL gets Vercel's 79-byte plain-text NOT_FOUND with no navigation, which is also what every expired result link will hit. 69 of 97 titles exceed 60 characters, 80 of them wasting 14 characters on a " — Wiser Walk" suffix for a brand nobody is searching for yet. The two game pages carry 165 and 172 words of crawlable text inside 245KB and 336KB of HTML, and link back into the site only twice and three times. If one thing gets fixed, make the 18 tradition pages genuinely distinct from one another, because they are the pages that answer the searches this site was built for.

## 1. [high impact / large effort / VISIBLE] The 18 tradition pages are 48% near-duplicates of each other and carry almost no prose
**Evidence:** I fetched all 18 /tradition/ pages live and compared their <main> text with 5-word shingles: mean Jaccard similarity 48.2%, max 68.5% between /tradition/eastern-orthodox/ and /tradition/catholic-roman-and-eastern/. Word counts run 327 to 349. Dumping the two most similar pages side by side, the shared text is roughly 200 words of fixed explainer ("Read this first... an approximate sketch of where typical adherents land, not official teaching", "Each arm is one axis: how far out you sit is how strongly you lean", "Both poles named on every rail", "In the hatched middle the quiz names neither pole", "By the same arithmetic the quiz uses", "Nearness is not agreement", "See how near you land. Answer the statements...", "18 statements About 3 minutes 6 axes, both poles named", "Suggest a correction"). The genuinely unique content on each page is six pole labels, six percentages and six neighbour names. There is not one sentence on /tradition/eastern-orthodox/ that explains the Orthodox view of communion in words; it says only "Table 90% toward Sacramental". For comparison the 11 articles sit at 8.8% mean similarity and the six theology-compass axis pages at 6.5%.

**Do:** Three moves, in order. (1) Shrink the boilerplate share: the "Read this first" note, the "Each arm is one axis" caption, the "Nearness is not agreement" note and the "Both poles named on every rail" kicker together are about 200 of 340 words. Keep the honesty, say each once and shorter, or put the two longest behind a <details>. That alone roughly halves the shingle overlap. (2) Make the meta description carry the page's own data instead of a template: replace site/src/pages/tradition/[slug].astro:66 with a description built from the tradition's actual pole words, e.g. for Eastern Orthodox "Eastern Orthodox on the Compass: firmly synergist on grace, sacramental at the table, continuationist on gifts, liturgical in worship. Beside 17 other traditions." (156 chars). Because the pole wording already differs per tradition (Orthodox is "firmly synergist", Catholic is "synergist-leaning"), every one of the 18 comes out different, and it is all data already on the page, so nothing is invented. (3) Build the /compare/[a]-vs-[b] pages already decided in the growth plan, but start with about 20 pairs people actually type (orthodox vs catholic, calvinist vs arminian, lutheran vs reformed, baptist vs presbyterian), not all 153. Google's spam policy defines scaled content abuse as "many pages are generated for the primary purpose of manipulating search rankings and not helping users", so a hand-picked handful is safe where an auto-generated 153 is not. Do NOT invent confession citations to pad these pages; CLAUDE.md forbids it and the audit would catch it.

**Where:** site/src/pages/tradition/[slug].astro:65-66 (title and description templates) and the page body below; measured on the live https://wiserwalk.com/tradition/* pages

## 2. [high impact / small effort] The sitemap has no lastmod on any of its 97 URLs
**Evidence:** curl https://wiserwalk.com/sitemap-0.xml returns 7,170 bytes containing 97 <loc> elements and zero <lastmod> elements (grep -c '<lastmod>' returns 0). The sitemap index at /sitemap-index.xml has no lastmod either. Google Search Central states: "Google uses the <lastmod> value if it's consistently and verifiably (for example by comparing to the last modification of the page) accurate", and separately that "Google ignores <priority> and <changefreq> values". So lastmod is the one optional sitemap field that still does anything, and the site emits none of it. @astrojs/sitemap does not add lastmod unless you pass it explicitly.

**Do:** In site/astro.config.mjs, inside the sitemap({...}) call at line 39, add a serialize function that stamps each entry with a truthful date. Articles already hold a real date (article.data.published, used at site/src/pages/articles/[slug].astro:76). For the generated reference pages, use the mtime or the audit data's changelog date rather than build time, because a sitemap that claims every page changed on every deploy is exactly the "not consistently and verifiably accurate" case Google says it ignores. If a truthful per-page date is not available for some group, omit lastmod for that group rather than faking it.

**Where:** site/astro.config.mjs:39-58 (the sitemap integration call; only a `filter` is passed, no `lastmod` or `serialize`)

## 10. [medium impact / small effort] IndexNow is not set up, so Bing, Yandex and Seznam learn about changes only by crawling
**Evidence:** No key file exists at the root of wiserwalk.com (checked several well-known paths; /llms.txt, /humans.txt, /ads.txt and /.well-known/security.txt all 404, and there is no *.txt key). IndexNow is described by Microsoft as "a free, open-source protocol empowering website owners with unprecedented control over how quickly their content is discovered". The protocol requires a key of 8 to 128 hex-ish characters in a UTF-8 text file at https://wiserwalk.com/{key}.txt, then a GET to https://<searchengine>/indexnow?url=...&key=... or a POST with up to 10,000 URLs. Google does not participate, so this is a Bing, Yandex, Seznam and Naver play, which matters because Bing's index also feeds DuckDuckGo, Yahoo and Ecosia.

**Do:** Generate a random key, commit it as site/public/<key>.txt containing only the key, and add a small post-build step (or a step in site/scripts/) that POSTs the sitemap's URLs to https://api.indexnow.org/indexnow with { host, key, urlList }. Wire it to run only on production deploys so preview builds do not spam it. Endpoints return 200 on success, 403 on a bad key and 429 if you submit too often, so submit changed URLs, not all 97 on every push.

**Where:** site/public/ (no key file); no submission step in site/scripts/ or site/package.json
