# speed-and-vitals

Wiser Walk is already a fast site, and that is the honest headline: the server answers the root document in 20 ms behind a Vercel cache hit, total blocking time is 0 ms on all eleven templates I measured, no page loads render-blocking JavaScript, below-the-fold images are lazy, LCP images carry fetchpriority=high with explicit width and height, and Lighthouse scores SEO 100 and best-practices 100 on every indexable template. Speed is therefore not what is holding this domain back, and I would not let it eat the budget that content and links deserve. Within the lens there are still four real defects. The biggest is that the Google Fonts stylesheet is render-blocking from a third origin on all 97 pages (490 to 800 ms of blocking per page) and the swap it causes is the sole measured source of layout shift on the site, pushing /q/theology-compass/ to CLS 0.16 and the result page to 0.196, both failing Google's 0.1 threshold; /q/theology-compass/ is the flagship indexable landing page, so that is the one outright Core Web Vital failure on a page meant to rank. Second, no image on the site has a srcset or a modern format, and I measured with sharp that AVIF at 900 px would cut the home page's image payload 41 percent (394 KB), /games/ by 84 percent (268 KB) and the textures behind every axis, tradition and figure page by 83 percent (105 KB), though the twenty-five Doré plates barely compress at all and should be left alone. Third, every static asset including the content-hashed /_astro/ files is served Cache-Control: public, max-age=0, must-revalidate, because the Vercel adapter's own immutable-cache route sits after the {"handle":"filesystem"} phase marker and so is never reached for files that exist; a four-line vercel.json fixes it. Fourth, Base.astro imports seven stylesheets, so one 141 KB CSS bundle is render-blocking on every page with 25 KB of it unused on the home page. The single most important thing is the font change: it fixes the only failing Core Web Vital, removes a cross-origin round trip from the critical path of all 97 pages, and changes nothing about how any page looks.

## 1. [high impact / medium effort / VISIBLE] Google Fonts blocks render on all 97 pages and its swap is the only cause of layout shift, failing CLS on the flagship quiz page
**Evidence:** Lighthouse 12 mobile on the live site: the fonts.googleapis.com stylesheet is the top render-blocking resource on every template measured, wasting 787-804 ms (home, /quizzes/, /q/theology-compass/, /r/, article, /articles/, axis, tradition, figure, /games/, /play/sounds-like-scripture/). The layout-shifts audit attributes 100 percent of measured CLS to font loads: /q/theology-compass/ CLS 0.1597 on <div class="runner"> caused by two DM Serif Display and two Poppins woff2 files (reproduced twice: 0.16 and 0.16); /r/theology-compass/01ZO4A/ CLS 0.1964 on <div class="panel layered result-panel">; /quizzes/ 0.018; /tradition/eastern-orthodox/ 0.037. Google's threshold is CLS below 0.1 (developers.google.com/search/docs/appearance/core-web-vitals). The cause is font-display: swap plus a metrically mismatched fallback: site.css line 23 sets --display: "DM Serif Display", Georgia, ... and DM Serif Display is markedly wider than Georgia, so the statement block reflows when the webfont lands. The critical path costs two extra origins: fonts.googleapis.com returns the CSS with Cache-Control: private, max-age=86400 (verified by curl), so it is re-fetched at least daily and cannot be shared by any CDN, and only then are the woff2 files on fonts.gstatic.com discovered. Five files, 97 KB total: Inter 47 KB, DM Serif Display roman and italic 17 KB each, Poppins 8 KB each.

**Do:** Self-host the five woff2 files that Google actually serves today (verified identical across the site and the two game pages) and drop the third-party stylesheet. Concretely: (1) download the five files listed in the evidence into site/public/fonts/; (2) in site/src/layouts/Base.astro delete lines 223-228 (both preconnects and the stylesheet link) and replace them with an inline <style> holding the five @font-face rules pointing at /fonts/*.woff2 with font-display: swap and unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, U+02C6, U+02DA, U+02DC, U+0304, U+0308, U+0329, U+2000-206F, U+20AC, U+2122, U+2191, U+2193, U+2212, U+2215, U+FEFF, U+FFFD (the latin subset only; the site has no Cyrillic or Greek copy); (3) add <link rel="preload" as="font" type="font/woff2" crossorigin> for the Inter file and the DM Serif Display roman file, which are the two needed for first paint; (4) add metric-matched fallbacks so the residual swap does not move anything, e.g. @font-face { font-family: 'DM Serif Fallback'; src: local('Georgia'); size-adjust: <computed>%; ascent-override: <computed>%; descent-override: <computed>%; line-gap-override: 0%; } and change site.css line 23 to --display: "DM Serif Display", "DM Serif Fallback", Georgia, "Times New Roman", serif (compute the percentages from the woff2 head and hhea tables with fontkit or opentype.js; do not guess them). Do the same edit in site/src/games/sounds-like-scripture.html lines 2-4 and site/src/games/who-said-it.html lines 2-4 so all pages share one font set and one cache entry. Pair this with the vercel.json header finding so /fonts/ is served immutable for a year. Nothing about the rendered type changes; the pages simply stop jumping.

**Where:** site/src/layouts/Base.astro lines 223-228; site/src/styles/site.css lines 23-25 (--display, --ui, --text); site/src/games/sounds-like-scripture.html lines 2-4; site/src/games/who-said-it.html lines 2-4; new files under site/public/fonts/

## 3. [medium impact / small effort] Every static asset is served max-age=0, must-revalidate, including the content-hashed /_astro/ files that are meant to be immutable
**Evidence:** curl -sI against the live site returns Cache-Control: public, max-age=0, must-revalidate for https://wiserwalk.com/_astro/about.BtdZgXeI.css, /img/hero-dawn.jpg, /img/sky-rays.jpg, /og/home.jpg, /tex/smokey.png and /favicon.ico alike. The build's own intent is the opposite: site/.vercel/output/config.json contains {"src": "^/_astro/(.*)$", "headers": {"cache-control": "public, max-age=31536000, immutable"}, "continue": true}. It never fires, because it is listed after {"handle": "filesystem"}, and Vercel's Build Output API reference defines that phase marker as "filesystem // check matches after the filesystem misses" and says "The routing system has multiple phases. The handle value indicates the start of a phase. All following routes are only checked in that phase." A file that exists never reaches the phase, so the header is dead code. The consequence is that every internal navigation and every repeat visit revalidates the whole asset set (14-20 requests per page) instead of reading it from disk, which on a phone on mobile data is a round trip the site does not need to spend. Lighthouse's uses-long-cache-ttl audit does not flag it, because Lighthouse treats max-age=0 plus must-revalidate as a deliberate opt-out, which is exactly why this has gone unnoticed.

**Do:** Add a headers block to site/vercel.json alongside the existing crons. Vercel's vercel.json reference gives the syntax and states of its own example that it "configures custom response headers for static files": {"headers": [{"source": "/_astro/(.*)", "headers": [{"key": "Cache-Control", "value": "public, max-age=31536000, immutable"}]}, {"source": "/fonts/(.*)", "headers": [{"key": "Cache-Control", "value": "public, max-age=31536000, immutable"}]}, {"source": "/(img|tex|og)/(.*)", "headers": [{"key": "Cache-Control", "value": "public, max-age=604800, stale-while-revalidate=86400"}]}]}. Use immutable only for /_astro/ and /fonts/, whose names contain a content hash or never change; give /img/, /tex/ and /og/ a week with stale-while-revalidate so a replaced painting still reaches people within a day. Leave the HTML alone: it must stay revalidating so a deploy is visible immediately. Verify after deploy with curl -sI https://wiserwalk.com/_astro/<hash>.css.

**Where:** site/vercel.json (currently only a crons key); evidence in site/.vercel/output/config.json routes array
